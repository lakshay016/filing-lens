# Reader-first development and design reviews

SPEC §14 sets the delivery order. Use this brief to run the next ticket and prepare each review. A review ends with a decision in SPEC §16 and a next ticket in TODO.md. The author brings the packet back to the product/technical lead in this chat or a new chat with the repository open. The implementer can investigate and fix ordinary bugs within the current ticket.

## R1. Build a baseline someone can read

**Question.** Can a reader see and verify what changed in one real Risk Factors section? Use Exxon Mobil (XOM), fiscal 2021, 2022 and 2023 as the development example. This reuses a company and two years already selected for parser fixtures. All three filings and both pairs are development material. Keep the company out of the held-out evaluation.

1. Add a one-ticker universe at `config/universes/demo.toml`. Set `name = "demo"`, `tickers = ["XOM"]`, `forms = ["10-K"]`, fiscal year bounds 2021 and 2023, and `store_raw = true`. Use the merged ingest command, `uv run fl ingest --universe demo`, then repeat it. Record the three original accession numbers, fiscal periods, acceptance dates, SEC primary-document URLs and the repeat-run fetch count. Investigate missing or duplicate years before comparing.
2. Build tasks 1.3, 1.4 and 1.5 in full, as their briefs specify, under `src/filinglens/parse/` (HTML to blocks, Item segmentation with the table-of-contents rule, paragraphs and hashes). Do not write a reduced Item 1A extractor: these components are needed again at R3 and the table-of-contents choice is the part a shortcut gets wrong. The fixture filings of brief 1.3 include XOM. Then extract Item 1A for the three demo filings, retaining original wording, order and headings. Check the first and last passage against each original, including the transition into the next Item. Verify the body was selected over the table of contents. Record any omitted tables or unreadable blocks. Report an extraction failure explicitly. The large-universe coverage run belongs to R3.
3. Add a reproducible CLI entry point, proposed as `uv run fl compare --universe demo --item 1A --out data/demo/index.html`. Put comparison and HTML rendering under `src/filinglens/compare/` and register the command in the existing CLI. Use Python's SequenceMatcher on ordered, lightly normalized paragraph text with autojunk disabled. Preserve numbers and original source text for display. Show replaced blocks as old/new groups so a positional guess cannot masquerade as a confirmed match. Keep unchanged passages accessible for context.
4. Generate one self-contained static HTML file showing both consecutive pairs. Include the company, fiscal years, filing dates, headings, numbered paragraphs, visible additions/deletions, and links to both SEC originals. Deep-link when the source has a verified anchor. Otherwise give the heading and a searchable phrase. Escape filing text as HTML. Open the file locally and follow a source link for each pair. A portable file suffices for review. A public demo can use the same artifact when the author chooses to publish.
5. Add offline tests for a table-of-contents heading, a section boundary, an unchanged passage, a numeric edit, a moved passage in baseline output, and safe rendering of markup. Reuse the existing test structure. Regenerate the page from the recorded inputs, run the repository checks in the briefs README, and record the command, commit and results.
6. Inspect each pair against its source and record the three most consequential observed baseline mistakes or limitations. For each, give old/new passage identifiers, what the page shows, what the source supports, and the consequence for a reader. Include at least one change the page handles well as a control. If fewer than three mistakes are found, report the actual count and the sections inspected. Keep implementation observations separate from human judgments of importance.

**Come back for review immediately after step 6.** Provide the HTML path or URL and a short review note in `docs/reviews/R1.md` with the input manifest, reproduction command, source checks, examples, and known omissions. A source extraction failure that prevents a credible comparison also warrants review, with the failing passage and attempted fix. The lead will inspect the examples, decide which extraction or display issues need fixing before reader sessions, and choose the tasks and comparison filings for R2. Advanced matching, training labels and a final company universe can wait.

## R2. Observe the reading task

Recruit two or three people who have read annual filings. Choose comparable development pairs separate from the R1 walkthrough. Ask the same question in both conditions: “Which changed disclosures would you brief a colleague on, and where is the supporting language?” Have an independent reader first mark must-see changes from the full original sections, blind to both outputs, with passage references and a short rationale. Freeze that list before the timed sessions.

Use each participant's usual workflow on one pair and Filing Lens on a different pair. Alternate pair assignments and which workflow goes first across readers. Capture elapsed time, referenced changes found, must-see changes missed, distracting alerts and any difficulty verifying evidence. Record per-reader and per-pair observations, anonymized. Note disagreements, small sample size and any unavailable judgments. The author organizes the sessions. An implementer may prepare the materials and must never invent reader feedback.

**Come back with** the task sheet, frozen reference list, timing and findings table, and two concrete successes or failures with source passages. **Decision:** fix extraction/navigation, develop a matching feature, improve ranking, retain the baseline, or stop. Choose the smallest change supported by the observations. If readers are unavailable, return with the baseline and describe the evidence gap.

## R3. Improve matching where the evidence warrants it

Select development and held-out companies before tuning. Keep all R1/R2 material in development. Use briefs 1.3–1.6 for broader parser coverage, then 1.9–1.10 for gold annotation and simple baselines. Use the labeler on original passages with exact matches only. Implement selected features from 1.7–1.8 individually and compare each with the baseline on the same development pairs. Preserve 1.11's frozen, single held-out run and the changed-paragraph metrics in SPEC §6.5. Keep examples and error counts for moves, splits, merges and spurious matches. Report coverage and exclusions alongside scores.

**Come back with** the development comparison, representative errors, and the proposed freeze before opening the test results. The lead chooses which features earn inclusion. Following the single test run, record the result even if it favors the baseline. Keep held-out results out of subsequent tuning.

## R4. Release the digest readers actually see

Add Item 7, Management's Discussion and Analysis. Start with deterministic ranking and source-linked evidence. For numeric alerts verify the same entity, measure and units on both sides, and disclose omitted tables. If testing a cross-company boilerplate discount, compare rankings with it on and off. Build peer frequencies using only filings accepted by the time of the target filing. Implement 1.13's classifier only after review identifies a ranking failure on development data that simpler rules leave unresolved.

Freeze the presentation, ranking and evaluation protocol before evaluating on unseen companies. Have an independent reader mark must-see changes from entire sections before showing any digest. Judge every displayed text and numeric alert. Record counts of useful and distracting alerts by type, must-see changes recovered out of the reference total, specific misses, elapsed review time against the usual workflow, and coverage failures. Record zero-reference filings separately. Precision@5 and classifier agreement, when applicable, are additional diagnostics. Keep reviewer disagreement visible.

**Come back with** the rendered digest, baseline comparison, per-filing counts and timings, the worst miss, and a reproducible results table. The lead decides whether to release the simplest version that helps readers find more must-see changes or finish faster without additional misses. Mixed results call for a narrower claim or another development iteration. Publish the measured outcome and limitations even if the baseline wins.

## R5. Decide whether history or Q&A earns further investment

After the digest review, try a disclosure-history view on real multi-year questions. Show each version, source year, and any break in continuity. Compare ordinary passage search with a fiscal-year filter against the same search over version chains, holding corpus, model, questions and retrieval budget fixed. Judge year correctness, evidence found, answer correctness and time. **Come back with** paired examples and results before choosing cited Q&A, a hosted interface, or further retrieval work. LLM summaries and MCP remain optional. The stock-return study is a separate, unscheduled research proposal.
