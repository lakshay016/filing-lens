## Candidates

A block (kind `heading` or `text`) is a candidate when its text matches, at the start,
case-insensitively:

```
^\s*items?\s+(\d{1,2}[abc]?)((?:\s*(?:,|and|&)\s*\d{1,2}[abc]?)*)\b\s*[\.:\-–—]?
```

and it is either a `heading` or at most 200 characters long. The codes found (upper-case)
must all be in `ITEM_ORDER`, otherwise it is not a candidate. A candidate with several
codes is a *combined heading* (`Items 1 and 2. Business and Properties`); its primary
code is the first one.

```python
@dataclass(frozen=True, slots=True)
class Candidate:
    block_index: int
    codes: tuple[str, ...]      # primary first
    gain: int
```

## The objective (read twice; this is where the task goes wrong)

`gain(c)` = the total number of characters of block text **strictly between candidate
`c` and the next candidate in the document, whichever Item that next candidate is**
(or the end of the document for the last candidate).

Choose a subsequence of candidates such that the primary codes are strictly increasing
in `ITEM_ORDER` position (for a combined heading every one of its codes must lie after
the previous chosen candidate's last code, and the next chosen candidate's primary code
must lie after this candidate's last code), maximising the **sum of gains**. Ties: prefer
the subsequence that chooses the later block (compare chosen block indices from the last
element backwards).

Why: in the table of contents the Item lines follow each other with almost nothing in
between, so each has a gain near zero; the body headings have their whole section as
gain. The tempting alternative, "maximise the text between consecutive *chosen*
headings", telescopes to "start as early as possible" and picks the table-of-contents
line for the first Item. Do not implement that.

Implementation: a simple O(n²) DP over candidates in document order
(`best[k] = gain[k] + max(best[p] for earlier p compatible with k, default 0)`), with
back-pointers. n is at most a few hundred.

## Sections

Chosen candidates `h_1 … h_m` in document order. The section of `h_k` runs from the
block **after** `h_k` up to (not including) `h_{k+1}`; the last runs to the end of the
document. Note the section ends at the next *chosen* heading, not the next candidate,
so a stray cross-reference line inside a section does not cut it. Blocks before `h_1`
form the `front` section. For a combined heading the whole section belongs to the
primary code and the other codes are recorded as combined.

```python
@dataclass(frozen=True, slots=True)
class Section:
    item: str                    # an ITEM_ORDER code or "front"
    heading_index: int | None    # block index of the Item heading; None for front
    start: int                   # first block index of the body
    end: int                     # one past the last block index
    chars: int                   # total characters of text and table blocks in the body
    combined: tuple[str, ...]    # other codes sharing this section

@dataclass(frozen=True, slots=True)
class Segmentation:
    sections: tuple[Section, ...]          # front first if non-empty, then document order
    status: Literal["ok", "partial", "failed"]
    notes: dict[str, Any]                  # stored in filing.parse_notes

def find_candidates(blocks: Sequence[Block]) -> list[Candidate]
def choose_headings(candidates: Sequence[Candidate]) -> list[Candidate]
def segment(blocks: Sequence[Block], period_of_report: date | None) -> Segmentation
def item_status(notes: Mapping[str, Any], item: str) -> Literal["ok", "short", "missing"]
```

## Status and notes

An Item is *found* if it is the primary code or a combined code of a chosen heading.
Per-Item status: `missing` if not found; `short` if the Item is in `SHORT_CHECKED`, is a
primary code, and its section has fewer than `ITEM_MIN_CHARS` characters; otherwise
`ok`. A combined (non-primary) code is `ok` and points at its primary.

Filing status:

- `failed` if fewer than three Items are found, or the document's total block text is
  under `DOC_MIN_CHARS`. Reasons: `too_few_items`, `too_short`.
- else `ok` if Items 1, 7 and 8 are each `ok`, and, when `period_of_report` is on or
  after `ITEM_1A_FROM` (or is unknown), Item 1A is `ok`.
- else `partial`, with reasons such as `missing:7`, `short:8`, `missing:1A`.

Item 1C, 9C and every other Item are never required.

```json
{
  "status_reasons": ["short:7"],
  "items": {
    "1":  {"status": "ok", "chars": 48211, "n_blocks": 143, "heading": "Item 1. Business"},
    "2":  {"status": "ok", "combined_into": "1"},
    "7":  {"status": "short", "chars": 412, "n_blocks": 2, "heading": "Item 7. ..."}
  },
  "combined": {"1": ["2"]},
  "n_candidates": 46,
  "total_chars": 512340
}
```

Items not found are simply absent from `items` (`item_status` returns `missing`).

## Pipeline and CLI

`parse/pipeline.py`:

```python
def parse_filing(session, filing: Filing, data_dir: Path) -> Segmentation | None
def parse_universe(session_factory, ciks: Sequence[int], data_dir: Path, *,
                   force: bool = False, limit: int | None = None) -> ParseSummary
```

`parse_filing`: read the raw file (`edgar.store.read_raw`), `extract_blocks`, `segment`,
then set `parse_status`, `parse_notes`, `parser_version = PARSER_VERSION`.
`NotHtmlError` → `failed` with reason `not_html`. Any other exception → `failed` with
reason `error:<ExceptionClass>` and the traceback logged; one bad filing never stops the
run. Filings are selected when `fetch_status = 'ok'` and (`parser_version` differs from
the current one or `force`). One transaction per filing. Paragraph storage is added by
task 1.5 inside this function; leave a clearly marked hook.

`fl parse`:

```
fl parse --universe NAME [--force] [--limit N]     parse, then print the report
fl parse --universe NAME --report                  print the report only
```

Report: a table by fiscal year with columns `filings | ok | partial | failed | % ok`,
a total row, then a list of status reasons with counts (most frequent first), then the
accession, company and reasons of every non-`ok` filing. "Never silently fill in a
failed parse": the report is how failures are seen.

## Unit tests (`test_items.py`, synthetic block lists built in code)

Helper: `doc(*specs)` builds blocks from `("h", "Item 1. Business")`, `("t", 5000)`
(a text block of that many characters).

1. Table of contents then body: TOC lists Items 1–15 back to back; body has the same
   headings with large sections → the body headings are chosen (assert on block
   indices) and the status is `ok`.
2. The trap: same document; assert that the heading chosen for Item 1 is the body one,
   not the TOC one, and that `front` contains the TOC.
3. A stray cross-reference: inside Item 7's body a short block `Item 1A. Risk Factors`
   → not chosen, Item 7's section is not cut.
4. A stray forward reference: inside Item 7 a short block `Item 8. Financial Statements
   and Supplementary Data` followed by 300 characters, then the real Item 8 heading
   followed by 50,000 → the real one is chosen.
5. Combined heading `Items 1 and 2. Business and Properties` → Items 1 and 2 found,
   section under `1`, `combined == {"1": ["2"]}`, `item_status(notes, "2") == "ok"`.
6. No Item 1A, `period_of_report = 2004-12-31` → `ok`; same with `2010-12-31` →
   `partial`, reason `missing:1A`.
7. Item 7 with 300 characters ("incorporated by reference") → `partial`, `short:7`.
8. Only two Items → `failed`, `too_few_items`. Total text 5,000 → `failed`, `too_short`.
9. Lower-case and odd punctuation: `ITEM 7A—QUANTITATIVE…`, `Item 9A(T).` (treated as
   9A), `Item 1A: Risk Factors`, `item 5 .`.
10. A text block of 500 characters starting with `Item 7 of this report` is not a
    candidate.
11. Out-of-order headings (Item 8 before Item 7 in the body) → the DP keeps the better
    in-order subset; the result is `partial`.
12. Determinism; and `choose_headings([])` → `[]`.
